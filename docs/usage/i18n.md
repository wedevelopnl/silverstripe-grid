# Internationalization (i18n)

The module ships with two locales (English and Dutch) and the tooling to extract translatable strings from both PHP and the React frontend. This guide covers using translations, adding new locales, and extracting strings in a new contribution.

## What's where

| Source | Consumer | Collected by |
|--------|----------|--------------|
| `lang/en.yml`, `lang/nl.yml` | SilverStripe `_t()` (PHP + .ss templates) | `dev/tasks/i18nTextCollectorTask` |
| `client/lang/src/en.json`, `client/lang/src/nl.json` | React `t()` helper at build time | `scripts/collect-js-i18n.mjs` (`npm run i18n:collect`) |
| `client/lang/en.js`, `client/lang/nl.js` | Browser runtime (bundled at build, loaded via `extra_requirements_i18n`) | Generated from the `src/*.json` during `npm run build` |

PHP strings flow through SilverStripe's standard mechanism. Frontend strings have a parallel stack so translations are available before `window.ss.i18n` finishes loading — the `t()` helper handles both cases transparently.

## Using translations

### In PHP

Standard `_t()` calls:

```php
_t(self::class . '.USE_GRID', 'Use grid on this page')
_t('WeDevelop\\Grid\\Model\\GridElement.DEFAULT_TITLE', '{type} {count}', ['type' => 'Section', 'count' => 1])
```

Placeholders use `{name}` syntax. Always provide the English fallback — collectors read it to populate `lang/en.yml` on first run and to catch missing-in-other-locales drift.

### In templates

`_t` is available in `.ss` templates as a SilverStripe built-in:

```silverstripe
<button><%t App\Something.SAVE 'Save' %></button>
```

### In TypeScript / React

Import the `t()` helper from the module's i18n entrypoint:

```ts
import { t } from '@/i18n';

t('App.Grid.SaveButton', 'Save');
t('App.Grid.ItemsCount', '{count} items', { count: 5 });
```

The helper delegates to `window.ss.i18n._t()` for the dictionary lookup and `window.ss.i18n.inject()` for placeholder substitution. When `ss.i18n` has not loaded yet (early boot), it falls back to the English string with local `{placeholder}` substitution.

Keys conventionally follow the dotted `Namespace.KEY` form. Collector tolerates any string but parity checks flag unmatched keys between locales.

### In `ValidationError`

Service-layer errors carry optional translation metadata:

```php
new ValidationError(
    message: 'Target parent does not match the claimed page.',
    field: 'ownership',
    code: ValidationErrorCode::OwnershipDenied,
    key: self::class . '.OWNERSHIP_PAGE_MISMATCH',
)
```

`ValidationError::translate()` resolves `key` through `_t()` with `params` as the injection map; when `key` is `null`, `message` is returned verbatim. The controller calls `translate()` when building JSON error responses so the frontend receives locale-appropriate text.

## Adding a new locale

1. **Copy the English file as a starting point.**

   ```bash
   cp lang/en.yml lang/fr.yml
   cp client/lang/src/en.json client/lang/src/fr.json
   ```

2. **Translate values.** The YAML file is keyed by class FQCN → constant name. The JSON file is a flat `{ key: translation }` map. Don't rename keys; collectors compare keys across locales.

3. **Register the locale via `FluentState` or the site's locale config** — this is a SilverStripe concern, not a module one.

4. **Run the parity check.**

   ```bash
   npm run i18n:check
   ```

   `i18n:check` runs a dry-run JS collect and verifies every key present in any `client/lang/src/*.json` is present in every other. The CI pipeline runs the same check so locale drift lands before merge.

## Extraction workflows

### PHP strings (from `_t()` in .php / .ss)

SilverStripe's built-in text collector reads all `_t()` calls and writes to `lang/*.yml`:

```bash
# Inside the Docker container (mounted via the lang/ volume)
vendor/bin/sake dev/tasks/i18nTextCollectorTask module=wedevelopnl-silverstripe-grid
```

Run this after adding new `_t()` calls. Commit the resulting changes to `lang/en.yml`.

### JavaScript strings (from `t()` in .ts / .tsx)

```bash
npm run i18n:collect      # Update client/lang/src/*.json in place
npm run i18n:check        # Dry-run collect + parity check (no writes)
```

`collect-js-i18n.mjs` scans `client/src/**/*.{ts,tsx}` for `t('key', 'fallback')` calls, preserves existing translations in other locales, and adds new keys with the English fallback. The parity script fails CI if any key is missing from one locale but not another.

Running `npm run build` automatically calls `i18n:collect` before Vite builds — the browser-bundled `client/lang/*.js` files are always in sync with the source `client/lang/src/*.json`.

### Regenerating browser bundles manually

```bash
npm run build    # Also invoked via `make dev-build` / `npm run dev`
```

The Vite build reads `client/lang/src/*.json` and writes `client/lang/*.js` files that SilverStripe's `extra_requirements_i18n` injects into the admin UI. You don't call this separately — any `npm run build` picks it up.

## Contributing translations

Pull requests adding a locale are welcome. A few rules:

- Every key present in `client/lang/src/en.json` must appear in every other locale file. The CI parity check enforces this.
- Keep the English source strings unchanged — adding a locale never edits `en.json` or `lang/en.yml`.
- Commit only source files. Generated browser bundles (`client/lang/*.js`) are regenerated by the build; don't edit them by hand.

## Debugging

- **"String shows the English fallback instead of my translation"**: the key is missing in the active locale. Run `npm run i18n:check` to spot the gap, or check the browser's network tab for the loaded `client/lang/{locale}.js` file.
- **"The React helper returns `undefined`"**: you called `t(key)` without a fallback. The helper requires a fallback string so first-paint never renders `undefined`.
- **"The backend error is still English in Dutch locale"**: confirm the calling code constructs the `ValidationError` with a `key` argument. Without `key`, `translate()` returns `message` verbatim.
